# Closed deployment failure reasons

The private forced-command operator now distinguishes identity/command/root preconditions, actual nonblocking lock contention, receive/verification, runtime preparation/activation and cleanup. Its failure response is `hsr-private-deployment-failure-v1` on stderr with exit3. The successful `hsr-private-deployment-v1` response remains unchanged and is printed only after owned staging cleanup completes.

Each failure carries a finite code and phase, the validated commit and run when available, failure-event persistence (`NotCreated`, `Persisted`, `Unavailable`), cleanup status and a separate cleanup code. Unaccepted commit/run values stay null. `AutomaticRetry` is false. An immutable Unconfirmed event includes only the same closed primary code/phase. Failure to write that event or clean staging cannot replace the original cause. Unknown exception text, paths, environment and commands never become diagnostic values.

`DEPLOY_LOCK_BUSY` means this process acquired no deployment authority: no incoming archive read, staging directory, runtime creation or release switch occurred. It neither proves the owner is stuck nor authorizes bypassing the lock, killing it or automatically replaying deployment/input. Inspect the existing owner and current health before a separately controlled action. Missing paths, filesystem denial and capacity exhaustion have their own closed codes; unrecognized causes remain `PRIVATE_DEPLOYMENT_UNCONFIRMED` with the observed phase. This is an operator diagnostic, never an accessibility barrier.

PSR-DEPLOY-002's earlier failure is retained. Its lock-collision explanation remains a hypothesis; adding this instrumentation does not retroactively establish that cause. PSR-DEPLOY-003 records the independently found early-success-output ordering. No service configuration, restart policy, privilege, host/egress boundary or website input capability changes.
