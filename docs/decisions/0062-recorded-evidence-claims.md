# Verify assessment claims against admitted originals

October 28, 2026. HTTP contract **1.9.0**, assessment policy
`hsr-website-evidence-v2`. Source implementation and delivery acceptance are
separate; see [validation](../validation/recorded-evidence-claims-v1.md).

Uploaded JSON can describe keys, a failed task, repeated attempts and a mouse
comparison. Matching file hashes prove that bytes were retained; they do not
establish those assertions. Real readiness now requires a trusted source proof
as well as the eight documentation conditions and original-file verification.
Examples remain fictional. Unbound imports remain suspected and cannot yield a
real Ready or a successful-task conclusion.

The existing assessment endpoint and private `evidence_assess` tool accept an
optional `admittedScanId`. The host resolves the original caller's current
workspace, scan, job, generation and worker receipt, reads all five complete
originals under bounded limits, verifies their hashes and producer manifest,
and validates the actual keyboard recording bundle. It rechecks authority after
each original and checks that the job is unchanged before releasing facts.
Changed or missing originals require a recording; no result is fabricated.

With only the admitted ID, the host projects the actual task, completed keys,
before/after focus, retained reader announcements, independent goal outcome,
one task attempt, environment and original references. With supplied JSON, it
compares those facts and reports contradictions explicitly. Reader commands in
one route are never separate repeat attempts. Current recordings supply no
trusted accessibility-failure diagnosis or mouse comparator; neither is invented.

Current admission runs the bundled synthetic shop. Its reserved identifier is
`https://synthetic-shop.invalid/`, not a visited public URL. `subjectKind` and
source proof explicitly say `ControlledFixture`. Such records cannot authorize
a real website evidence package. Reached can support a limited no-blocking-
barrier result for that controlled task; Unknown and timeout remain insufficient.

New recordings retain full actual accessibility observations in `observation.json`
and collector-read browser, Playwright and operating system, plus the configured
viewport context, in
`traversal.json`. The archive still has five originals. Older originals remain
unchanged: missing context stays missing, and a starting-state-only observation
is `BaselineOnly`, insufficient for the required accessibility snapshot bundle.

The separate Lovable consumer uses the existing Supabase Edge operation and
never evaluates the policy. It presents a saved-test selector, the source check,
eight plain-language questions, missing records and a next step. Export repeats
the original authorized request. The attorney-facing reference informs copy;
Privensic Screen Reader remains the product name. No human-review task is added.
Disability, personal encounter/injury, standing, liability and admissibility
remain outside this automated website-side assessment.
