# Retained native ownership and recovery

The isolated worker previously held its container name/owner only in memory. A crashed coordinator could leave a container after losing that identity. Native ownership is now persisted before any container create request. This adds a process-restart recovery boundary; database lease expiry still does not prove native cleanup.

The operator-private evidence directory contains a .runtime journal. Each immutable intent binds schema, random owner nonce, tenant/scan/job/generation, runtime and exact image ID. The file is create-only, flushed to disk before native allocation, and named by its nonce. No database connection, lease token or storage capability is recorded. An exclusive file lock spans startup recovery, queue polling and native execution, preventing another coordinator using this same state directory from reconciling active work.

Startup reads and validates the complete retained inventory before making a destructive runtime call. Size, JSON shape, schema, descriptor, file/owner identity, runtime and immutable image are checked. A runtime change fails closed rather than assuming an old container is absent in the new engine. A malformed or incomplete filesystem record remains an explicit startup failure requiring operator repair; it never silently authorizes cleanup or retry. This scope covers retained valid intents after a process stops, not arbitrary filesystem corruption or whole-host power-loss durability.

Recovery looks up only the derived random container name. Its owner, tenant, scan, job, generation and actual image must match the retained intent. Mismatch, unavailable runtime or uncertain removal halts recovery and retains the intent. The narrow cleanup operation independently confirms absence through the actual engine. It records an immutable removal acknowledgement before retiring the intent. An exact acknowledgement retry preserves the earlier record; a conflicting identity prevents retirement. Removal facts say container absence was observed; they do not invent a timely Chromium shutdown, reader result or verified goal.

Normal execution also records confirmed container removal before returning observation bytes. A native journal failure remains Unconfirmed and cannot release the database job as safely stopped. The worker halts on unconfirmed ownership/cleanup. A restarted coordinator reconciles retained resources before acquiring new work; the database then independently enforces capability expiry, generation and read-only retry limits. Native recovery never completes a queued observation or acknowledges a database message.

Operator command `HeadlessScreenReader.Worker --recover` performs only this retained-resource reconciliation and needs no database credential. It still requires the operator's fixed runtime/image/evidence configuration and exclusive state lock. It is intended for the trusted supervisor/deployment path. It grants no browser input or remotely callable destructive API.

Acceptance retains the actual Chromium/database completion path and adds controlled retained-intent recovery with real native containers. One bounded sleeper represents an interrupted owned container; an independent sentinel must survive. A mismatched owner must remain running and its intent must remain. The proof explicitly does not claim that this sleeper scenario is an actual crash of a Chromium session. Separately, actual Chromium observation/shutdown and actual Linux SIGTERM continue to be tested. The Linux integration also starts a real polling worker and verifies a second process cannot acquire the same ownership directory.

Private VPS provisioning, CI deployment, operational readiness, rollback, live JWT onboarding and private S3 finalization remain subsequent gates. Do not enable automatic restart that bypasses this startup reconciliation. Public MCP hosting and plugin publication remain deferred.
