# Owned browser shutdown and failure receipts

The private-viewer main push exposed a Windows shutdown failure in the earlier controller CLI. [CI 39521143289](https://github.com/jvelezc/ai-screen-reader/actions/runs/39521143289) passed all 1,065 tests on both Windows and Ubuntu, but Windows then failed the controller demonstration with CONTROL_CLOSE_UNCONFIRMED. Its retained files show three stored commands, final acknowledged exclusion and OWNED_CLOSE_STARTED, with no Closed journal. The exact SDK shutdown call was not recorded. Ubuntu, both headed Linux/Docker cases and public isolation passed; the overall run was failed, not accepted.

Source inspection found two hazards: context close could wait indefinitely before whole-browser close was attempted, and a repeated adapter DisposeAsync could return merely because disposal had started. The repair removes those hazards and records sanitized shutdown stages if another failure occurs. It does not claim the unrecorded SDK stage was empirically identified.

## Shutdown sequence

Admission closes before shutdown. The adapter caches one actual disposal task, including reentrant callers. Collector stop retains its existing five-second acknowledgement bound and actual task. A failed or timed-out collector stop still leads to native cleanup, but remains a failure even if Chromium closes or the collector eventually acknowledges.

After collector stop, context close has a one-second soft budget. Missing or failed context acknowledgement triggers whole-browser close. Context and browser now share one four-second native budget: a fast context lends its unused time to browser shutdown; a context consuming the full second leaves at most three seconds. This replaces the original fixed one-plus-three split, preserving its four-second maximum and the outer ownership deadline. The budget does not restart when browser close begins, and already completed calls cannot acknowledge an exhausted budget. This is escalation against the privately owned browser instance, not a process-name/PID kill. Owned transport disposal then settles outstanding protocol callbacks. Every actual collector/context/browser task remains joined; a timed-out wait cannot release actual work. Browser/transport failures remain faulted after late acknowledgements. A settled per-context failure may be superseded by acknowledged whole-browser closure; both facts remain visible.

The existing five-second controller/owned close deadlines are unchanged. If actual shutdown cannot finish within the owning deadline, the owner remains faulted and cannot grant a replacement controller. A late native close does not recover it. A hung native call remains visible and keeps the actual disposal task pending.

## Independent owned process exit

CI39534740390 measured three Windows native-deadline failures at final elapsed times of 4,101 to 5,515 ms. Context calls had acknowledged without escalation, browser calls eventually acknowledged, and no SDK call was rejected. The exact browser-process exit time was still unmeasured. Sharing the wait budget did not eliminate the failures.

Each fixture/public browser factory now obtains the root PID from its own Chromium CDP SystemInfo response and retains a read-only Process handle and OS exit notification. It looks up no process by name, kills no process and deletes no directory. The handle is released before actual adapter disposal completes. Normal launches cannot substitute a caller-provided PID or exit assertion.

Native shutdown supervises SDK response and independently confirmed root-process exit under the same four-second wait budget. If positive OS exit precedes the SDK's final response, it can stop its own Playwright transport and join every actual context/browser/process callback. If exit remains unconfirmed after two seconds of total native time, it now stops that privately owned transport earlier, reserving the remaining native budget for actual exit confirmation. Context close consumes part of this grace period; it does not restart at browser close. SDK acknowledgement or transport disposal alone cannot release a still-pending exit watch. A rejected SDK call, failed process watch, expired deadline or unsettled callback remains failed; positive late exit cannot recover it. Existing collector/evidence-write acknowledgements and the five-second outer ownership deadline remain required.

ProcessExitConfirmed, ProcessCallSettled, TransportEscalatedAfterProcessExit and BrowserCloseAcknowledgedBeforeTransport preserve these separate facts. This certifies root-process exit, API transport disposal and actual protocol-call drain. It does not certify SDK temporary-directory erasure or all descendant/driver process cleanup outside the disposable Linux container. Credential entry and general recording remain gated; container/display/image cleanup continues to have independent receipts.

CI39539944407 again passed all five Linux jobs, including Ubuntu1,171/1,171, but Windows failed two frame tests with1,169/1,171 passed. Contexts acknowledged, while root-exit confirmation and SDK responses were still pending at the four-second wait deadline. After owned transport stop, actual cleanup settled at4,127 and5,656ms. These observations motivate the two-second soft transport escalation; they do not establish why native graceful close stalled. TransportEscalatedBeforeProcessExit means the owned transport stop began before exit confirmation, not that exact kernel exit time was measured. Transport disposal is attempted exactly once, including reentrant callers. All actual calls remain joined, disposal cost consumes the original budget, and a transport failure stays faulted. Production adds no process-name lookup, OS kill or directory deletion.

## Evidence and limits

Optional platform-independent BrowserShutdownStatus records phase, actual pending count, each call's settled/acknowledged state, transport disposal, context escalation and a fixed safe error code. It includes no exception text, command line, URL, bearer or screenshot. It is diagnostic evidence, not reader-visible semantics or an accessibility-barrier classification.

CI39538136292 passed Ubuntu's 1,171 cases and every independent Linux job, but Windows failed two of 1,171 cases: a bundled paragraph fixture exceeded its inherited five-second input timeout while loading, and the recorded route viewer received CHROMIUM_BROWSER_CLOSE_UNCONFIRMED. The recording helper had kept only the error code, losing the new shutdown facts. Bundled initialization now explicitly uses the existing fifteen-second startup allowance while still waiting for the complete load, including child documents. Interactive operations and all capture/controller/shutdown deadlines remain unchanged. Recording receipts now retain typed shutdown facts and final monotonic native elapsed time; route acceptance failures print only those safe facts. The cause of that unmeasured close remains unresolved until remote validation supplies evidence.

Additive BrowserDeadlineExceeded and BrowserCallRejected facts distinguish a deadline from an actual rejected call. Native failures include only this sanitized status and monotonic native elapsed milliseconds in an inner diagnostic exception, so TRX failures retain the stage without exposing the native exception. Pixel proof receipts retain the same safe shutdown status. The shared-budget repair follows recurring Windows close failures in CI39532356790; sequential tests did not eliminate them. Source inspection confirms that the pinned driver waits for temporary-directory cleanup as part of browser close, but the failed CI did not measure that as its cause. Repaired remote acceptance remains required.

The controller CLI now keeps execution and cleanup failures separately in controller-demo.json and prints an explicit unsuccessful summary. Its original controller.json retains the hsr-local-controller-v1 shape with additive shutdown diagnostics. A minimal internal workflow seam reuses IScreenReaderBrowser and IOwnedEvidenceStore; production still creates real Chromium and real owned files. Deterministic failure tests use in-memory dependencies without environment/console mutation or filesystem I/O. Real Chromium disposal and the full acceptance demos remain separate checks.

SDK acknowledgement and actual process exit remain separate. The headed/private-viewer proofs also verify process exit and task-owned cleanup explicitly. This repair adds no OS-level process killing, privileges, arbitrary target or public viewer. The [pixel relay](0033-private-pixel-viewer.md) is implemented locally; its six-job remote acceptance must pass before the [accessible viewing client](0033-private-pixel-viewer.md#next-accessible-private-viewing-client). See [shutdown validation](../validation/browser-shutdown-v1.md).
