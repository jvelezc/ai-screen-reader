# Owned browser shutdown and failure receipts

The private-viewer main push exposed a Windows shutdown failure in the earlier controller CLI. [CI 39521143289](https://github.com/jvelezc/ai-screen-reader/actions/runs/39521143289) passed all 1,065 tests on both Windows and Ubuntu, but Windows then failed the controller demonstration with CONTROL_CLOSE_UNCONFIRMED. Its retained files show three stored commands, final acknowledged exclusion and OWNED_CLOSE_STARTED, with no Closed journal. The exact SDK shutdown call was not recorded. Ubuntu, both headed Linux/Docker cases and public isolation passed; the overall run was failed, not accepted.

Source inspection found two hazards: context close could wait indefinitely before whole-browser close was attempted, and a repeated adapter DisposeAsync could return merely because disposal had started. The repair removes those hazards and records sanitized shutdown stages if another failure occurs. It does not claim the unrecorded SDK stage was empirically identified.

## Shutdown sequence

Admission closes before shutdown. The adapter caches one actual disposal task, including reentrant callers. Collector stop retains its existing five-second acknowledgement bound and actual task. A failed or timed-out collector stop still leads to native cleanup, but remains a failure even if Chromium closes or the collector eventually acknowledges.

After collector stop, context close has a one-second soft budget. Missing or failed context acknowledgement triggers whole-browser close. Context and browser now share one four-second native budget: a fast context lends its unused time to browser shutdown; a context consuming the full second leaves at most three seconds. This replaces the original fixed one-plus-three split, preserving its four-second maximum and the outer ownership deadline. The budget does not restart when browser close begins, and already completed calls cannot acknowledge an exhausted budget. This is escalation against the privately owned browser instance, not a process-name/PID kill. Owned transport disposal then settles outstanding protocol callbacks. Every actual collector/context/browser task remains joined; a timed-out wait cannot release actual work. Browser/transport failures remain faulted after late acknowledgements. A settled per-context failure may be superseded by acknowledged whole-browser closure; both facts remain visible.

The existing five-second controller/owned close deadlines are unchanged. If actual shutdown cannot finish within the owning deadline, the owner remains faulted and cannot grant a replacement controller. A late native close does not recover it. A hung native call remains visible and keeps the actual disposal task pending.

## Independent owned process exit

CI39534740390 measured three Windows native-deadline failures at final elapsed times of 4,101 to 5,515 ms. Context calls had acknowledged without escalation, browser calls eventually acknowledged, and no SDK call was rejected. The exact browser-process exit time was still unmeasured. Sharing the wait budget did not eliminate the failures.

Each fixture/public browser factory now obtains the root PID from its own Chromium CDP SystemInfo response and retains a Process handle and OS exit notification. A second response through that same browser reconfirms the root after its handle is acquired, rejecting a vanished root before granting stop capability. It looks up no process by name and deletes no directory. The handle is released after actual adapter shutdown joins all calls. Normal launches cannot substitute a caller-provided PID or exit assertion. The original version only watched exit; the Windows-only retained-handle fallback below now also permits stopping that owned root.

Native shutdown supervises SDK response and independently confirmed root-process exit under the same four-second wait budget. If positive OS exit precedes the SDK's final response, it can stop its own Playwright transport and join every actual context/browser/process callback. If exit remains unconfirmed, the scoped Windows root-stop path has one second of graceful allowance; the driver-only path has250ms, reserving3,750ms for its measured cleanup cost. Both use the original native origin and four-second exit-confirmation deadline. Context close consumes part of this grace period; it does not restart at browser close. SDK acknowledgement or transport disposal alone cannot release a still-pending exit watch. A rejected SDK call, failed process watch, expired deadline or unsettled callback remains failed; positive late exit cannot recover it. Existing collector/evidence-write acknowledgements and the five-second outer ownership deadline remain required.

ProcessExitConfirmed, ProcessCallSettled, TransportEscalatedAfterProcessExit and BrowserCloseAcknowledgedBeforeTransport preserve these separate facts. This certifies root-process exit, API transport disposal and actual protocol-call drain. It does not certify SDK temporary-directory erasure or all descendant/driver process cleanup outside the disposable Linux container. Credential entry and general recording remain gated; container/display/image cleanup continues to have independent receipts.

CI39539944407 again passed all five Linux jobs, including Ubuntu1,171/1,171, but Windows failed two frame tests with1,169/1,171 passed. Contexts acknowledged, while root-exit confirmation and SDK responses were still pending at the four-second wait deadline. After owned transport stop, actual cleanup settled at4,127 and5,656ms. These observations motivated the two-second soft transport escalation; they do not establish why native graceful close stalled. TransportEscalatedBeforeProcessExit means escalation was chosen while confirmation was unavailable; it measures neither exact kernel exit time nor worker start time. Transport disposal is attempted once, including reentrant callers. That earlier transport repair added no process-name lookup, OS kill or directory deletion; the Windows owned-root extension below is a later change.

## Independently tracked transport stop

CI39544123526 passed Ubuntu1,186/1,186 and every independent Linux job. Windows verified the twenty-marker recording at120.7ms maximum conservative error, but passed1,184/1,186 overall: one native close settled at5,600ms after early transport stop, and one deterministic controller test asserted DrainingCalls before its disposal callback had returned. The latter was a test coordination race. The native receipt did not measure process confirmation and transport duration separately, so it cannot establish which native work consumed that time.

Synchronous Playwright disposal previously blocked the monitoring continuation. It now runs as one cached, isolated blocking operation while the four-second exit monitor remains active. ActiveCalls includes its pending work. TransportCallSettled and TransportDisposed distinguish completion from acknowledgement; TransportStopDurationMilliseconds and ProcessExitConfirmationMilliseconds retain separate monotonic facts. Root confirmation must be recorded strictly before4,000ms, including when a task finishes before WaitAsync registers a timer. A late coordinator continuation may join an already timely confirmation; a confirmation at4,000ms or later cannot recover failure. The full regression caught that exact-boundary timer-registration race before this repair was published.

Every actual collector/context/browser/process/transport call remains joined. Root confirmation within four seconds does not release a pending transport or SDK callback. An adapter can finish draining after that root-confirmation window; the separate controller still faults at five seconds if actual cleanup is incomplete and cannot recover after late completion. A failed disposal remains faulted even with timely root exit. The actual call is never replaced with a cancelled wait. Tests now wait for callback settlement and phase transitions rather than treating a signal inside a callback as evidence that it returned.

## Evidence and limits

### Windows retained-handle root stop

CI39655895713 passed all six Linux jobs, including Ubuntu1,234/1,234, but Windows passed1,233/1,234. An existing diagnostic fixture confirmed root exit at5,138.2443ms, transport stop duration3,156.519ms and final native elapsed5,158.8587ms. The root confirmation itself was late; this was not just a timer-registration or monitoring-continuation race. The pinned Playwright driver source uses a synchronous taskkill tree command during repeated Windows graceful shutdown. That source behavior is not proof that the failed run spent its time in that command.

Windows adapters now offer a root-stop capability bound to the process handle retained during their own CDP-validated launch. A second SystemInfo response after opening the handle confirms it still belongs to the same live browser. At one second of native time, if exit is still unconfirmed, shutdown requests that one root stop on a tracked isolated worker. The [.NET Windows implementation](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Diagnostics.Process/src/System/Diagnostics/Process.Windows.cs) reuses the stored handle for Process.Kill rather than reopening a numeric PID. No name search, process-tree walk or caller-supplied PID is introduced. Linux retains the existing owned-driver path.

The native callback's return only acknowledges the request. [Process termination is asynchronous](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-10.0), so the independent watch must still confirm exit strictly before4,000ms. OwnedProcessStopRequested, OwnedProcessStopCallSettled, OwnedProcessStopAcknowledged and request duration preserve separate facts; ActiveCalls includes a pending root-stop callback. Transport disposal follows root confirmation, or starts as fallback after a rejected request. A rejected root-stop request remains a sanitized sticky failure even if transport later closes Chromium. Actual SDK rejection also remains failed; force stop does not manufacture its acknowledgement. Every actual callback, including root stop, remains joined and the outer5,000ms ownership deadline remains unchanged.

The real integration witness deliberately replaces the SDK-response callback while retaining an actual Chromium context, owned handle and native exit watch. It verifies the platform-specific root capability and that another separately launched browser remains alive and usable. Ordinary fixtures and the full acceptance demos exercise actual SDK close callbacks. Root exit does not certify all descendant processes or SDK profile erasure outside a disposable container; credentials and general recording remain gated.

Optional platform-independent BrowserShutdownStatus records phase, actual pending count, each call's settled/acknowledged state, transport disposal, context escalation and a fixed safe error code. It includes no exception text, command line, URL, bearer or screenshot. It is diagnostic evidence, not reader-visible semantics or an accessibility-barrier classification.
